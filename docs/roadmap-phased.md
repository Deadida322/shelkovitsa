## Этап 1 — заказ и остатки (быстрый win)

1. **Телефон с маской**  
   - UI: маска `+7 (###) ###-##-##` остаётся.  
   - Перед `POST /api/order` (и в DTO/pipe на сервере): вычищать до `+7XXXXXXXXXX` / E.164.  
   - Тесты: маска → 201; кривой номер → 422.

2. **Отмена → возврат остатка**  
   - Статус отмены (или явный `cancelled`).  
   - В той же транзакции: `increment` amount по позициям заказа (один раз, идемпотентно).  
   - Запретить «отменить уже отменённый».  
   - E2e: заказ → cancel → остаток как до заказа.

3. **Checkout hardening** (то, что «не понял» — см. ответы)  
   - Нормализация телефона.  
   - `region`: обычный `text` (не `email`).  
   - Disable кнопки / анти-даблклик; `.catch` + toast ошибки; не чистить корзину при ошибке.  
   - Qty: `max` = `maxAmount` с позиции корзины, не 1000.

4. **Админка заказов**  
   - Колонки: телефон, сумма (`formatRub`), комментарий.  
   - Пока письма нет — хотя бы видно, кому звонить.

**Критерий готовности:** заказ с маской телефона проходит; отмена возвращает склад; ошибки checkout видны пользователю.

## Этап 2 — почта вместо Telegram

1. Выбрать транспорт: SMTP (Yandex / Mail.ru / SendGrid / Amazon SES — по стенду).  
2. Модуль `MailService` (Nodemailer или аналог): шаблоны HTML/text.  
3. **Письмо себе (админу)** при новом заказе: ФИО, тел, mail, адрес, состав, сумма, id.  
4. **Письмо клиенту**: «заказ принят», номер, состав, «ожидайте связи».  
5. Выключить / оставить Telegram опционально через env (`TELEGRAM_ENABLED=false` по умолчанию на проде, если почта ок).  
6. **Сброс пароля:** токен + TTL в БД, `POST /auth/forgot`, `POST /auth/reset`, страница `/recover` бьёт в API; письмо со ссылкой.  
7. Env: `SMTP_*`, `MAIL_FROM`, `MAIL_ORDER_TO` (куда слать себе).

**Критерий:** заказ → письмо админу и клиенту; recover реально меняет пароль.

## Ответы на вопросы

### Поиск — как улучшить, нужны ли индексы?

Сейчас: `ILike('%query%')` по `article`, `name`, `description`, `brand` — **обычный B-tree почти не помогает** для `%…%` (leading wildcard).

**Стоит сделать по шагам:**

1. **Сразу (дёшево):**  
   - btree/unique уже на `article` — для точного артикула сначала искать exact/prefix (`query%`) отдельной веткой;  
   - btree на `brand` (lower) — фасеты и фильтр бренда.  
2. **Правильное улучшение ILIKE:** расширение **`pg_trgm`** + GIN/GIST trigram на `name`, `brand`, при необходимости `article`. Это ускоряет `%подстрока%`.  
3. **Позже, если каталог > десятки тысяч и поиск критичен:** `tsvector` / Full-Text Search по RU, или внешний движок (Meilisearch/Typesense). Для текущего объёма обычно хватает **trgm + аккуратный SQL**.

Индексы — да, но **не «просто INDEX на name»**, а **trigram** (или FTS). Иначе пользы мало.

### Картинки — Nuxt Image, где хранить?

Сейчас контракт хороший: в БД ключ файла, фронту **`/static/<ключ>`**; бэкенд — `LocalFileStorage` или `S3FileStorage` (`STORAGE_DRIVER`). Менять схему хранения не нужно.

**Оптимально:**

| Среда | Хранение | Отдача |
|-------|----------|--------|
| Dev / маленький стенд | local (`DEST_PATH`) | Nest `ServeStatic` / middleware `/static` |
| Прод | **S3-совместимое** (RustFS/MinIO/Yandex Object Storage) | Публичный URL бакета **или** прокси `/static` с редиректом (уже заложено в `static.middleware`) |
| CDN | перед S3 (Cloudflare / Selectel CDN) | Nuxt Image ходит на CDN-домен |

**Nuxt Image:** заменить `<img>` в карточках на `<NuxtImg>` / `<NuxtPicture>` с `sizes`, WebP/AVIF, lazy. Provider: кастомный или `ipx` с `baseURL` = API `/static` (или CDN). Оптимизация может быть:

- **на лету (ipx)** — просто, нагрузка на Node;  
- **заранее / CDN image resize** — лучше для прода при трафике.

Локально + S3 — оба ок; для прода предпочтительнее **S3 (+ CDN)**, локальный диск — только если один сервер и бэкапы диска настроены.

### Cookie + sameSite

Сейчас в production: `sameSite: 'none'` + `secure: true` — это для **кросс-сайт** (фронт и API на разных сайтах без общего родителя).

Если фронт и API same-site (например `shelkovitsa.ru` + `shelkovitsa.ru/api` или `api.` как related — уточнить деплой): достаточно **`sameSite: 'lax'`**, `secure: true` на HTTPS, `httpOnly: true` для `access_token`.  
`none` оставлять только если реально разные registrable domains.

CSRF: при `lax` + JSON API риск ниже, чем с form-POST; токен CSRF — по желанию позже.

### Checkout — что имелось в виду

Не «переписать checkout», а дыры:

1. Телефон с маской уходит как есть → 422.  
2. Нет обработки ошибки заказа (silent fail), возможен даблклик.  
3. Счётчик количества до 1000, игнор остатка (`maxAmount`).  
4. Корзина чистится только в success-пути — при ошибке ок, но UX ошибки нет.

Это чинится в этапе 1 вместе с телефоном.

### `region` — что лучше

Сейчас `type="email"` на поле региона — баг (браузерная валидация «как email»).  
**Сделать `type="text"`**, `autocomplete="address-level1"`, при желании maxlength. Отдельный справочник регионов — только когда появится доставка.

### Cookie `user` — что предлагаю

`user` — **не httpOnly**, хранит fio/isAdmin для UI. Права реально с `/api/auth/me`, но:

- `getMe` вызывается **только если** в cookie уже есть `fio` — после истечения token UI может «думать», что вы залогинены, пока не сходит me; наоборот, после login ок.  
- Можно подделать `isAdmin: true` в cookie — UI покажет шестерёнку, middleware всё равно не пустит на `/admin`, но мигание/лишние запросы.

**Предложение:**

1. Короткосрочно: всегда дергать `/api/auth/me` при старте приложения (layout), не только при наличии `fio`; при 401 чистить `user`.  
2. Среднесрочно: не писать `isAdmin` в cookie — только display-поля после успешного `me`; или держать user в **памяти Pinia** + optional `localStorage` без роли.  
3. Источник правды всегда сервер (уже так для API).

### 401 в `$api` — кейсы и как исправить

Сейчас **любой** 401 → `clearUser` + `navigateTo('/signin')`.

**Кейсы, где это ломает UX:**

| Кейс | Что происходит |
|------|----------------|
| Гость открыл `/api/auth/me` или защищённый метод | Редирект на signin (если me дергается через `$api`) |
| Истекла сессия на витрине/корзине sync | Выкидывает на signin посреди каталога |
| Админский 401 vs «просто не залогинен» | Одинаково |
| Фоновый poll / вторичный запрос | Уводит со страницы |

**Как исправить:**

1. **Не редиректить глобально.** В `onResponse`: только `clearUser()` при 401; редирект — опционально.  
2. Редирект на `/signin`, если:  
   - запрос был к заведомо auth-required (`/api/user/*`, `/api/admin/*`, `/api/order` GET «мои»), **или**  
   - текущий route защищён middleware (`/admin`, ЛК).  
3. Для публичных (`/api/product-article`, guest order POST) 401 почти не бывает; если будет — **не** слать на signin.  
4. `getMe` при отсутствии сессии: ожидать 401 и тихо `user = null`, без navigate.  
5. Опционально: код/флаг `skipAuthRedirect` в опциях `$api`.
