## 1. Что сделано на ветке

Прод был потерян и поднимается с нуля, поэтому схема БД и API переписаны без обратной
совместимости.

### Бэкенд

| Область | Что сделано |
|---|---|
| Исправления по ревью | заказы (цены, остатки, транзакции), авторизация и проверка ролей, импорт, инфраструктура Nest; фронт — выход из аккаунта, проверка админа, цены в заказах (минимальные правки, UI-библиотеки не трогали) |
| БД | новая схема одной миграцией, роли пользователей, мягкое удаление через `@DeleteDateColumn`, явные списки сущностей и миграций |
| API | REST: чтение через GET, админка под `/api/admin`, id в путях; ответы через `ClassSerializerInterceptor` и DTO (`PaginatedDto`); strict TypeScript, удалён мёртвый код. Описание — [API.md](API.md) |
| Импорт каталога | учитывает категорию и сам создаёт категории/подкатегории; остаток «>5» → 5; размеры, которые Excel превратил в даты, восстанавливаются (`45750` → «3/4»); построчные транзакции, фото качаются после коммита строки |
| Excel | свой потоковый ридер (yauzl + saxes) вместо node-xlsx, защита от zip-бомб, XXE и «billion laughs», лимиты на строки/колонки/ячейку; файл сначала проверяется целиком, и только потом чистится каталог. Подробнее — раздел 3 |
| Загрузка файлов | случайное имя на диске, лимит размера в multer на каждый запрос (413 сразу), формат по сигнатуре; `.xls` отклоняется с подсказкой пересохранить |
| Хранилище фото | `FileStorage`: локальный диск или S3 (`STORAGE_DRIVER`), в docker-compose — RustFS (образы MinIO недоступны); `npm run storage:init` |
| Зависимости | Node 20 → 24, Nest 10 → 12 (ESM, Express 5), Jest → Vitest, без `nestjs-telegraf`, `nestjs-form-data`, `@nestjs/passport`; `npm audit` — 0 уязвимостей (overrides: `qs`, `multer` 2.5, `uuid` для exceljs) |
| Инструменты разработки | docker-compose с Postgres, `npm run seed` / `db:reset` / `create-admin`, скрипт бэкапа, проверка `/api/health` в деплое |

## 3. Разбор Excel: как устроено и почему так

[src/helpers/excelHelper.ts](../src/helpers/excelHelper.ts):

- `readSheetRows(path | Buffer)` — строки первого листа по одной (async-генератор);
  `readSheet` — все строки; `buildXlsx` — запись (exceljs).
- Zip открывается по центральному каталогу (yauzl): порядок частей в архиве не важен, временных
  файлов нет. yauzl сверяет фактический размер распакованных данных с заявленным, поэтому лимиты
  по каталогу честные.
- Лимиты по умолчанию (`DEFAULT_EXCEL_LIMITS`): 1000 файлов в архиве, 256 МБ после распаковки,
  сжатие ≤ 100× для частей > 1 МБ, 100 000 строк, 200 колонок, 32 767 символов в ячейке.
  Реальная выгрузка: 31 МБ XML, сжатие ~8×.
- Числа отдаются числами, стили не читаются: Excel-даты остаются серийными номерами — так их и ждёт
  `normalizeSupplierSize`.
- Ошибки формата и лимитов — `ExcelFileError` → 400 с текстом для пользователя.

**Почему не exceljs для чтения.** Потоковое чтение exceljs 4.4.0 имеет два известных открытых бага
(исправления в PR годами не принимаются, релизов с 2023 года нет):

- кириллица и другие многобайтовые символы превращаются в «�» на границах чанков —
  [#2063](https://github.com/exceljs/exceljs/issues/2063), [#2084](https://github.com/exceljs/exceljs/issues/2084);
  у нас «Дикий_имбирь» читался как «��икий_имбирь», 3 строки выгрузки переставали сопоставляться;
- чтение теряет `xl/workbook.xml`, когда лист лежит в архиве раньше sharedStrings (так сохраняет
  Excel), — `Cannot read properties of undefined (reading 'sheets')`,
  [#3064](https://github.com/exceljs/exceljs/issues/3064); причина — unzipper 0.10 и пауза потока
  в `iterate-stream.js`.

Настройками это не обходится, только патчами библиотеки. Решили держать свой ридер, exceljs оставить
для записи.

**Проверка.** Отчёт `audit:marketplace` по `shel_data_new.xlsx` совпадает с прежним (node-xlsx)
полностью. Мутационная проверка: каждая защита и ключевое поведение ридера и импорта ловятся
тестами. Вредоносные файлы через HTTP (zip-бомба 200 МБ в 204 КБ, XXE, «billion laughs», обрезанный
zip, .xls, текст, 22 МБ) отклоняются за 50–100 мс, каталог при `isDeletedOther=true` не меняется.

## 4. Вопросы и замечания по файлам соответствий

Файлы `server/data/colors.xlsx` (890 строк) и `server/data/sizes.xlsx` (385 строк): первый столбец —
значение у поставщика, второй — в каталоге. Импорт берёт пару из них; `InitService` при старте
создаёт в БД все значения второго столбца. Ключи нормализуются так же, как значения выгрузки:
цвет — первая буква заглавная, остальные строчные (`000_Бежевый` → `000_бежевый`), размер — верхний
регистр. Регистр в файле поэтому не важен.

### 4.1. Противоречивые строки (исправить в файлах)

| Файл | Значение поставщика | Строки | Ведёт на | Что происходит сейчас |
|---|---|---|---|---|
| `colors.xlsx` | Прозрачный | 512 и 574 | «Прозрачный» и «Разноцветный» | побеждает последняя строка: прозрачные товары попадают в каталог как «Разноцветный»; цвет «Прозрачный» создаётся в БД, но не используется |
| `sizes.xlsx` | 46D/L | 244 и 245 | «48D» и «48L» | побеждает «48L» |

**Вопрос заказчику:** какое соответствие правильное? Для «46D/L», вероятно, нужен отдельный размер
каталога, а не одна из двух половин.

**Предложение по коду:** при загрузке справочника проверять дубли ключа с разными значениями и
показывать ошибку в админке, а не молча брать последнюю строку.

### 4.2. Значения выгрузки, которых нет в файлах (дополнить файлы)

**Цвета — 576 строк, 34 значения:**

- **504 строки бренда Belweiss** (и 5 — Valeria Lingerie): цвет указан числовым кодом — `10`, `11`,
  `1`, `9`, `25`, `43`, `51`, `16`, `29`, `8`, `22`, `14`, `59`, `85`, `19`, `79`, `80`, `73`, `34`,
  `74`, `9000`, `61`, `58`, `707`, `71`, `9003`, `63`, `2935`. **Нужна палитра Belweiss**
  (код → цвет) от поставщика. Один и тот же код у разных брендов может значить разное — если коды
  встретятся у другого бренда, ключ придётся делать «бренд + код».
- **62 строки без цвета** — бренды Lolita, Julimex, Amelie, Mioocchi, Mia-Mia, Albina L,
  Philippe Matignon, Gentlemen. Вопрос: это товары без цвета (аксессуары, бретели) — тогда нужен
  цвет каталога «Без цвета», — или пропуск в выгрузке?
- единичные: `Blu/Turchese`, `131_Turquoise`, `TI_мелкий_узор/бирюзовый`, `BI_Какаду/Голубой`,
  `OI_Черепаха/Коралловый`.

**Размеры — 139 строк, 7 значений:**

| Размер | Строк | Комментарий |
|---|---|---|
| `UN` | 117 | универсальный: бретели (50), сопутствующие товары (41), трусы, подвязки, пояса… Нужен размер каталога, например «Единый» |
| пусто | 10 | пропуск в выгрузке |
| `45/47` | 4 | вероятно, носки/чулки |
| `3/4`, `5/6`, `9/10`, `11/12` | 8 | детские размеры (Excel превращал их в даты — импорт уже восстанавливает); нужны размеры каталога |

### 4.3. Склейка вариантов — нужно решение

Если два цвета поставщика сопоставлены одному цвету каталога, у артикула получается **один вариант**
(артикул + цвет + размер), и **остаток последней строки затирает предыдущий**, а не складывается.

Пример — артикул `1030217Ут`, размер M:

| Код поставщика | Цвет поставщика | Остаток | Цвет каталога |
|---|---|---|---|
| 1030217Ут-мд | Dune | >5 | Бежевый |
| 1030217Ут-мнл | Nilo | 2 | Бежевый |

В каталоге остаётся один вариант «Бежевый, M» с остатком 2.

По всей выгрузке: **2 609 строк склеиваются в 1 230 вариантов**, 1 379 вариантов поставщика
пропадают как отдельные.

Для Маркета это критично: `offerId` = код варианта поставщика (уникален), а у нас таких вариантов
меньше. Остатки на Маркет пришлось бы отдавать по склеенному варианту.

Варианты решения:

1. **Суммировать остатки** склеенных строк — минимальная правка импорта; покупатель видит один
   «Бежевый», но цвета поставщика различимы только по фото.
2. **Хранить вариант поставщика отдельно:** у варианта каталога — код поставщика (`offerId`) и цвет
   поставщика, цвет каталога — только для фильтра. Правильнее для Маркета (1:1 с выгрузкой), больше
   работы.
3. **Сделать цвета каталога точнее** (Dune → «Песочный», Nilo → «Нюдовый») — правка файла, склеек
   станет меньше, но не ноль.

Рекомендация: вариант 2 вместе с этапом «Модель» интеграции (там всё равно добавляются GTIN, вес и
габариты у варианта). До этого — вариант 1 как быстрая защита от потери остатков.

Текущее поведение зафиксировано тестом «два цвета поставщика → один цвет каталога» в
[test/import.e2e-spec.ts](../test/import.e2e-spec.ts) — при изменении логики его нужно обновить.

## 6. Следующие шаги по интеграции

По плану из [INTEGRATION_YANDEX.md](INTEGRATION_YANDEX.md#5-план-работ):

1. **Модель** (не зависит от заказчика): GTIN, вес и габариты у варианта, вариант поставщика
   (п. 4.3), импорт штрихкода с проверкой (`gtin.ts` готов), структурированный адрес и ПВЗ у заказа,
   источник заказа, сущность «Отправление».
2. **Яндекс Доставка**: модуль API, расчёт и выбор ПВЗ при оформлении, заявка, статусы, ярлыки —
   после кабинета Доставки.
3. **Оплата** — после решения бизнеса.
4. **Яндекс Маркет**: маппинг категорий, выгрузка каталога, цены и остатки, заказы — после кабинета.
5. **Маркировка** — после регистрации в ГИС МТ.
