# Интеграция с Яндекс Доставкой и Яндекс Маркетом

Анализ возможности интеграции: что проверено на практике, что нужно доработать в коде и каких
данных не хватает. Проверка данных — на реальной выгрузке поставщика `temp-dev/shel_data_new.xlsx`
(35 829 вариантов, 4 586 артикулов) командой `npm run audit:marketplace`.

Что уже сделано на ветке, свежие цифры импорта и открытые вопросы по файлам соответствий цветов и
размеров — [INTEGRATION_STATUS.md](INTEGRATION_STATUS.md).

## Коротко

| | Возможно? | Главный блокер |
|---|---|---|
| **Яндекс Доставка** (доставка заказов с сайта в ПВЗ и курьером) | Да, API подходит полностью | Нет веса и габаритов товаров; нет договора и склада в кабинете Доставки |
| **Яндекс Маркет** (продажа каталога на маркетплейсе) | Да | Маркировка «Честный знак» (бельё — обязательная с 2025 г.); маппинг категорий и характеристик; 6,5% штрихкодов — внутренние |

Обе интеграции упираются не столько в код, сколько в **данные и юридическую часть**: вес/габариты,
GTIN, коды маркировки, договоры. Код можно писать параллельно с подготовкой данных.

Итог: **92,2% вариантов (85,8% артикулов целиком) проходят обязательные поля карточки Маркета**;
**0% готово к Доставке** — нет веса и габаритов.

Найдено при проверке:

- **Excel портит данные.** Детские размеры «3/4», «11/12» сохранены как даты (число 45750 = 03.04.2025).
  Импорт теперь восстанавливает их (`normalizeSupplierSize`), но в `sizes.xlsx` таких размеров нет.
  В `shell_data_short.xlsx` штрихкоды испорчены необратимо (`8,42209E+12`). Выгрузку нужно делать
  с текстовым форматом колонок «Штрих-код» и «Размер».
- **28% строк — в псевдокатегориях**, а не в типах товара: «Коллекция …» (10 112), «Распродажа»
  (1 086), «Образцы» (902), «Некондиция» (101), «Уценка» (26). Маркету нужен тип («Бюстгальтер»),
  и на нашем сайте это тоже засоряет каталог.
- **Остаток «>5» у 12 845 строк (36%)** — точное количество неизвестно. Импорт берёт 5; для Маркета
  это риск продать больше, чем есть, либо недопоказ остатка.
- **Импорт не читает штрихкод вообще**, и в БД для него нет поля.

### Яндекс Доставка — тестовый контур

Запросы к `b2b.taxi.tst.yandex.net` с публичным тестовым токеном из документации:

| Метод | Результат |
|---|---|
| `location/detect` | ✔ «Москва» → `geo_id` 213 |
| `pickup-points/list` | ✔ 838 ПВЗ в Москве, из них **94 с примеркой** (`is_fitting_allowed`) |
| `offers/create` (наш товар, ПВЗ и курьер) | Запрос проходит валидацию; варианты не выдаются: публичный тестовый склад без настроенных заборов (`pickups_not_configured`, `no_delivery_options`) |
| `offers/create`, курьер с оплатой картой при получении | ✘ `card_on_receipt` для курьера запрещён — нужен `postpay` |
| `pricing-calculator` | `no_delivery_options` — та же причина |

Вывод: формат заказа подходит, полный цикл (заявка → подтверждение → ярлык → статусы)
проверим на своём тестовом складе после подключения кабинета. Важно для белья: **примерка**
(`fitting` у позиции и `is_fitting_allowed` у ПВЗ) и **частичный выкуп** (`particular_items_refuse`).

У Маркета публичной песочницы нет: все методы требуют API-ключ кабинета продавца.

## 2. Яндекс Доставка

### Какой продукт

- **«Доставка в другой день»** (API платформы, `/api/b2b/platform/…`) — ПВЗ, постаматы и курьер
  по России. Основной вариант для магазина.
- «Экспресс» (`/b2b/cargo/integration/v2/claims…`) — курьер за 1–2 часа по городу. Имеет смысл
  позже, только для Москвы и при наличии склада в городе.

### Как это будет работать

```
Покупатель                Сайт (бэкенд)                       Яндекс Доставка          Склад магазина
    │ выбирает ПВЗ на карте   │                                        │                        │
    │ или вводит адрес ──────►│ расчёт стоимости и срока ─────────────►│ pricing-calculator     │
    │◄── цена и срок ─────────│                                        │                        │
    │ оформляет заказ ───────►│ заказ (+ оплата онлайн, если выбрана)  │                        │
    │                         │ админ подтверждает заказ               │                        │
    │                         │ offers/create → offers/confirm ───────►│ заявка, request_id     │
    │                         │ ярлык и акт в админке ◄────────────────│                        │
    │                         │                                        │◄── забор / сдача в СЦ ─│ упаковано, ярлык
    │                         │ опрос статусов (cron) ◄────────────────│ в пути, в ПВЗ, выдан   │
    │◄── письмо о статусе ────│ статус заказа у нас                    │                        │
```

### 2.1. Что делает заказчик

Порядок важен: шаги 1–5 дают разработчику доступ к боевому API, без них заявки не создаются.
Шаги 6–9 можно делать параллельно.

**1. Зарегистрировать кабинет компании.**

- Открыть [dostavka.yandex.ru/auth/list](https://dostavka.yandex.ru/auth/list), войти через Яндекс ID.
  Лучше завести отдельный аккаунт компании (например, `shelkovitsa.dostavka@yandex.ru`), а не личный:
  к нему будут привязаны токен и доступ сотрудников.
- Указать название магазина — его видят покупатели в уведомлениях Доставки.
- Ввести и подтвердить ИНН, принять
  [оферту для корпоративных клиентов](https://yandex.ru/legal/logistics_corporate_prepaid_offer/).
  Нужен **расчётный счёт ИП или ООО**: при оплате картой аккаунт считается частным (C2C), и
  корпоративные возможности — API, наложенный платёж — недоступны.
- Подтвердить регистрацию: пополнить баланс от 1 ₽ или подписать оферту через ЭДО (Диадок, Saby).
  Через ЭДО может открыться приветственный лимит — заказы без пополнения баланса.

Источник: [Подключить сервис](https://yandex.ru/support/delivery-profile/ru/other-day/how-to-join.md).

**2. Выбрать, как платить за услуги Доставки.**

| Вариант | Как работает |
|---|---|
| Предоплата | баланс пополняется по счёту, доставки списываются с него; первый платёж от 500 ₽, зачисление до 3 рабочих дней |
| Постоплата | счёт за месяц, оплатить до 15 числа; закрывающие документы — в течение 7 дней после конца месяца |

Источник: [Оплата услуг](https://yandex.ru/support/delivery-profile/ru/other-day/pay.md).

**3. Решить, как отдавать посылки Доставке.**

| Способ | Когда подходит | Условия |
|---|---|---|
| Курьерский забор со склада | регулярные отгрузки | доступен в Москве, Санкт-Петербурге, Екатеринбурге и ряде других городов; заявка в «Календаре отгрузок» (адрес, объём, вес, слот); цена зависит от региона и объёма; до 50 заказов, 1 м³ и 50 кг — без паллет |
| Самостоятельно в сортировочный центр | склад рядом с СЦ, большие партии | адреса и часы работы — в разделе «Склады для отправки» |
| Самостоятельно в ПВЗ | мало заказов | до 50 коробок размера S или M за раз |

Источник: [Способы и правила отгрузки](https://yandex.ru/support/delivery-profile/ru/other-day/rules.md).

**4. Получить ID станции отгрузки** (в API — `platform_station_id`).

- *Забор со склада:* в кабинете → «Адреса» → «Добавить адрес»: адрес склада, название, контакт
  представителя, email для уведомлений курьера → «Сохранить». Затем запланировать отгрузку с этого
  адреса в «Календаре отгрузок» и написать в чат поддержки в кабинете — специалист выдаст ID станции.
  Если отгрузка пока не нужна, её можно бесплатно отменить до 16:00 МСК накануне.
- *Сдача в СЦ:* ID станции указан в таблице
  [«Склады для отправки»](https://yandex.ru/support/delivery-profile/ru/other-day/warehouses.md).

Источник: [Добавить избранные адреса](https://yandex.ru/support/delivery-profile/ru/other-day/add-address.md).

**5. Получить токен API.**

- В кабинете: вкладка «Интеграция» → «Активируйте интеграцию» → «Получить токен». Токен потом виден в
  «Профиль компании» → «Токен для API».
- Токен бессрочный, но **смена пароля кабинета его аннулирует** — после смены пароля нужен новый токен
  и замена на сервере.
- Передать разработчику защищённо (менеджер паролей, зашифрованный архив), не открытым текстом в
  мессенджере: токен даёт право создавать заявки за счёт магазина.

Источник: [Доступ к API](https://yandex.ru/support/delivery-profile/ru/api/other-day/access).

**6. Реквизиты для заявок** — у бухгалтерии: ИНН продавца и ставка НДС на товары
(0, 5, 7, 10, 22% или «без НДС»). Передаются в каждой позиции заявки.

**7. Вес и габариты упаковки по типам товаров.**

Мерить каждый артикул не нужно: достаточно 2–3 типоразмеров упаковки на тип товара. Заполнить таблицу
и прислать разработчику (или добавить колонками в выгрузку — см. документ для заказчика):

| Тип товара (как в выгрузке) | Упаковка | Длина, см | Ширина, см | Высота, см | Вес брутто, г |
|---|---|---|---|---|---|
| Трусы *(пример заполнения, не замер)* | пакет S | 25 | 18 | 2 | 80 |
| Бюстгальтеры | … | … | … | … | … |
| Купальники | … | … | … | … | … |

Вес брутто — товар в упаковке, на кухонных или почтовых весах. Размеры — упакованной посылки,
с округлением вверх до сантиметра. Ограничения ПВЗ — 30 кг, сторона до 150 см, сумма сторон до 300 см
([лимиты](https://yandex.ru/support/delivery-profile/ru/other-day/weight-limits.md)); бельё в них
укладывается с большим запасом.

**8. Упаковка и маркировка посылок.** Каждый заказ упаковывается отдельно, так, чтобы вскрытие было
заметно; пустоты заполняются. Ярлык печатается из нашей админки и клеится на видное место; если мест
несколько — ярлык на каждом. Внутрь — копия ярлыка или упаковочный лист
([правила упаковки](https://yandex.ru/support/delivery-profile/ru/other-day/packing-rules.md)).

**9. Решения по условиям доставки** — от них зависит, что разработчик включит в оформление заказа.

| Вопрос | Варианты | Что учесть |
|---|---|---|
| Как платит покупатель | онлайн на сайте / при получении / оба | при получении (наложенный платёж): деньги покупателя сначала покрывают услуги Доставки (тариф, эквайринг, процент от стоимости), остаток ежедневно перечисляется на расчётный счёт; онлайн — нужен платёжный сервис (ЮKassa и т. п.) и онлайн-касса |
| Куда доставлять | ПВЗ и постаматы / курьер / оба | курьер дороже, нужен точный адрес и интервал |
| Примерка | разрешить / нет | только в ПВЗ с примеркой: в Москве 94 из 838 |
| Частичный выкуп | разрешить / нет | покупатель забирает часть заказа; для белья с примеркой обычно нужно вместе |
| Кто платит за доставку | покупатель по тарифу / бесплатно от суммы / фиксированно | влияет на расчёт в корзине |
| Объявленная ценность | полная стоимость / меньше | это страховка посылки; от неё зависит процент в стоимости услуг |

**Что передать разработчику — чек-лист**

- [ ] токен API (защищённо)
- [ ] ID станции отгрузки и способ отгрузки (забор / СЦ / ПВЗ)
- [ ] ИНН и ставка НДС
- [ ] таблица веса и габаритов по типам товаров
- [ ] решения по п. 9
- [ ] контакт сотрудника, который будет отгружать заказы (для доступа в кабинет — раздел
  «Сотрудники»)

### 2.2. Что делает разработчик

Шаги 1–4 и 6–9 можно делать сейчас на тестовом контуре, до кабинета заказчика:
`https://b2b.taxi.tst.yandex.net`, публичный тестовый токен и станция из
[документации](https://yandex.ru/support/delivery-profile/ru/api/other-day/access). Тестовый контур
работает только по Москве; расчёт стоимости на публичной станции не выдаётся (не настроены заборы) —
полный цикл проверяется на станции заказчика.

**1. Модель данных** (миграция).

| Где | Сейчас | Нужно |
|---|---|---|
| Упаковка | нет | сущность «Профиль упаковки» (название, `dx`/`dy`/`dz` см, вес брутто г), привязка к подкатегории; переопределение у артикула — по необходимости |
| `Order` | `fio`, `tel`, `region`, `address` строками | имя и фамилия отдельно (в API `first_name` обязателен), телефон в формате `+7…`, структурированный адрес (город, улица, дом, квартира, индекс, координаты), ID выбранного ПВЗ, стоимость доставки, способ оплаты, источник заказа |
| `DeliveryType` | справочник с названием | код провайдера: `yandex_pickup`, `yandex_courier`, `manual` (самовывоз, Почта и т. п. остаются ручными) |
| Отправление | нет | новая сущность: заказ, `request_id`, `operator_request_id`, выбранный оффер, статус и история статусов, штрихкоды мест, ссылка на ярлык |
| `OrderStatus` | `create`, `in_work`, `payment`, `delivery`, `close` | сопоставление статусов Доставки: в пути → `delivery`, выдан → `close`, отмена и возврат — новые статусы или отметка |

**2. Конфигурация.** Переменные `YANDEX_DELIVERY_BASE_URL`, `YANDEX_DELIVERY_TOKEN`,
`YANDEX_DELIVERY_STATION_ID`, `YANDEX_DELIVERY_INN`, `YANDEX_DELIVERY_NDS`, флаг
`YANDEX_DELIVERY_ENABLED`; проверка в `env.validation`, описание в
[ENV_VARIABLES.md](ENV_VARIABLES.md). Токен не попадает в логи и ответы API.

**3. Клиент API — `YandexDeliveryModule`.** `fetch` с таймаутом, повтор при 429/5xx с паузой,
понятные ошибки для админки. Единицы API: деньги в **копейках**, вес в **граммах**, размеры в **см**,
время в UTC; конвертация — в одном месте, с unit-тестами.

**4. Оформление заказа** (бэкенд + минимальные правки фронта в `client/pages/deliver.vue`).

- ПВЗ: [виджет](https://yandex.ru/support/delivery-profile/ru/modules/widgets.md)
  (`YaDelivery.createWidget`, событие `YaNddWidgetPointSelected` → `detail.id`, адрес); фильтры —
  способ оплаты (`postpay` / `already_paid`) и примерка (`pickup_services.is_fitting_allowed`), вес в
  граммах — виджет скрывает неподходящие ПВЗ. Виджет считает по публичным тарифам, поэтому
  итоговую цену даёт наш бэкенд.
- Курьер: форма структурированного адреса.
- Эндпоинт расчёта, например `POST /api/delivery/quote` (корзина + ПВЗ или адрес) →
  `pricing-calculator`; интервалы курьера — `offers/info`. Стоимость доставки входит в сумму заказа.

**5. Создание заявки** — по кнопке в админке после подтверждения заказа (или после онлайн-оплаты).

- `offers/create`:
  - `info.operator_request_id` — номер нашего заказа (повтор запроса не создаёт дубль);
  - `source.platform_station.platform_id` — станция заказчика;
  - `destination` — `platform_station` (ПВЗ) или `custom_location` (адрес);
  - `items[]` — `article` (код варианта), `name`, `count`, `place_barcode`,
    `billing_details.unit_price` и `assessed_unit_price` (копейки), `inn`, `nds`; позже
    `marking_code` («Честный знак») и `fitting`;
  - `places[]` — `barcode`, `physical_dims.weight_gross` (г), `dx`/`dy`/`dz` (см) из профиля
    упаковки;
  - `billing_info.payment_method` — `already_paid` или `postpay` (для курьера `card_on_receipt`
    запрещён — проверено на тестовом контуре), `delivery_cost` при оплате при получении;
  - `recipient_info` — имя, телефон, email; `last_mile_policy` — `self_pickup` или `time_interval`;
    `particular_items_refuse` — по решению о частичном выкупе.
- Выбрать оффер (дешевле или быстрее — настройка) → `offers/confirm` → сохранить `request_id` в
  отправлении. Оффер живёт ограниченное время: при ошибке — пересоздать.

Справочник:
[offers/create](https://yandex.ru/support/delivery-profile/ru/api/other-day/ref/3.-Osnovnye-zaprosy/apib2bplatformofferscreate-post.md),
[offers/confirm](https://yandex.ru/support/delivery-profile/ru/api/other-day/ref/3.-Osnovnye-zaprosy/apib2bplatformoffersconfirm-post.md).

**6. Админка.** В карточке заказа: создать заявку, скачать ярлык
([`request/generate-labels`](https://yandex.ru/support/delivery-profile/ru/api/other-day/ref/4.-Yarlyki-i-akty-priema-peredachi/apib2bplatformrequestgenerate-labels-post.md)),
акт приёма-передачи для отгрузки
([`request/get-handover-act`](https://yandex.ru/support/delivery-profile/ru/api/other-day/ref/4.-Yarlyki-i-akty-priema-peredachi/apib2bplatformrequestget-handover-act-post.md)),
отменить ([`request/cancel`](https://yandex.ru/support/delivery-profile/ru/api/other-day/ref/3.-Osnovnye-zaprosy/apib2bplatformrequestcancel-post.md)),
текущий статус и история.

**7. Статусы.** Вебхуков в API «в другой день» нет — опрос по cron (как ретраи Telegram в
`order-notification.service.ts`): активные отправления через
[`requests/info`](https://yandex.ru/support/delivery-profile/ru/api/other-day/ref/3.-Osnovnye-zaprosy/apib2bplatformrequestsinfo-post.md)
за интервал или `request/info` по одному; при смене — статус заказа по
[статусной модели](https://yandex.ru/support/delivery-profile/ru/api/other-day/status-model.md),
уведомление покупателю и админу.

**8. Ошибки и крайние случаи:** адрес не распознан, ПВЗ закрылся после оформления, вес вне лимитов
ПВЗ, оффер истёк, частичный выкуп и возврат (возврат остатка на склад), недоступность API — заказ
сохраняется, заявка создаётся повторно из админки.

**9. Тесты.** Unit — конвертация единиц, сборка тела `offers/create`, сопоставление статусов. E2E —
с локальным HTTP-сервером вместо API Доставки (как сервер картинок в `test/import.e2e-spec.ts`).
Ручная проверка — тестовый контур, затем станция заказчика.

**10. Запуск.** Переменные на сервере, токен заказчика, первая заявка на реальном заказе с отменой,
затем — боевой режим.

### 2.3. Зависимости

| Работа разработчика | Можно начать | Нужно от заказчика для запуска |
|---|---|---|
| Модель данных, конфигурация, клиент API | сейчас | — |
| Оформление: виджет, расчёт, адрес | сейчас (тестовый контур) | решения по п. 9 (оплата, ПВЗ/курьер, примерка) |
| Профили упаковки | сейчас (структура) | таблица веса и габаритов (п. 7) |
| Создание заявки, ярлык, акт, статусы | сейчас (тестовый контур, Москва) | токен, ID станции, ИНН и НДС (п. 4–6) |

## 3. Яндекс Маркет

### Модель работы

| Модель | Кто хранит и доставляет | Подходит |
|---|---|---|
| **DBS** | склад и доставка — продавец (можно через Яндекс Доставку) | ✔ проще всего: свой склад, своя логистика, коды маркировки не проверяются в ГИС МТ при приёмке Маркетом |
| **FBS** | склад продавца, доставка — Маркет | ✔ если удобнее отгружать Маркету; коды маркировки проверяются |
| FBY | склад Маркета | позже, при большом обороте |

Рекомендация: начать с **DBS** (или FBS) — товар остаётся на своём складе, остатки общие с сайтом.

### Как устроена интеграция (Partner API)

1. **Каталог**: `POST v2/businesses/{businessId}/offer-mappings/update` — `offerId` (наш код варианта),
   `name`, `marketCategoryId` (листовая категория), `pictures` (1–30 постоянных ссылок), `vendor`,
   `description` (≤ 6000), `barcodes` (GTIN), `weightDimensions` (см, кг), `manufacturerCountries`,
   `parameterValues` (характеристики категории: размер по сетке, цвет, состав, пол…); до 100 товаров
   за запрос. Характеристики — `offer-cards/update`.
2. **Цены и остатки**: отдельные методы цен и остатков (`offers/stocks`) — по cron и при изменении.
3. **Заказы**: уведомления Маркета на наш эндпоинт или опрос списка заказов → создание заказа у нас
   с источником «Маркет», резерв остатка, смена статусов (принят, собран, отгружен).
4. **Маркировка**: коды «Честного знака» по каждой единице —
   `PUT v2/campaigns/{campaignId}/orders/{orderId}/identifiers` (DBS) или `…/boxes` (FBS).
5. **Возвраты и отмены**: обработка статусов и возврат остатка.

### Что доработать в коде

- **Вариант товара**: `barcode` (GTIN) — сейчас колонка выгрузки игнорируется; вес и габариты (общие
  с Доставкой); `marketSku` и статус карточки на Маркете.
- **Маппинг категорий**: таблица «категория/тип поставщика → листовая категория Маркета» и набор
  характеристик категории (размерная сетка, цвет Маркета, пол, материал). 185 пар категория/тип в
  выгрузке, из них 28% строк — псевдокатегории, их тип придётся выводить из названия.
- **Тексты**: описания короче 400 символов у 90% — нужна доработка контента (вручную или генерацией).
- **Модуль `YandexMarketModule`**: клиент API (ключ `Api-Key`, лимиты), синхронизация каталога,
  цен и остатков (cron + по событию), приём заказов, статусы, маркировка.
- **Общий остаток**: заказы с сайта и с Маркета списывают один склад — нужна быстрая выгрузка
  остатков на Маркет после каждого заказа, иначе перепродажа.
- **Заказ**: поле источника (сайт / Маркет), внешний номер заказа.

### Каких данных не хватает

| Данные | Объём | Где взять |
|---|---|---|
| **Коды маркировки «Честный знак»** на каждую единицу | весь ассортимент | регистрация в ГИС МТ, заказ кодов у производителя/поставщика или самостоятельно |
| GTIN вместо внутренних штрихкодов | 2 343 варианта | GS1 RUS (префикс предприятия) или у поставщика |
| Исправить невалидные штрихкоды | 11 | поставщик |
| Описания ≥ 400 символов | ~90% | контент |
| Сопоставить цвета и размеры | 576 + 139 строк | дополнить `colors.xlsx`, `sizes.xlsx` |
| Тип товара для псевдокатегорий | 28% строк | правила по названию или вручную |
| Вес и габариты | 100% | замер |
| Кабинет продавца, `businessId`, `campaignId`, API-ключ | — | регистрация на Маркете (ИП/ООО) |
| Размерные таблицы | по брендам | производители / таблицы Маркета |

## 4. Маркировка «Честный знак» — до любых интеграций

Нижнее бельё, купальники, чулочно-носочные изделия и домашняя одежда входят в «третью волну»
обязательной маркировки лёгкой промышленности (Постановление Правительства № 883, 2024 г., старт
в 2025 г.). Это касается **и продаж на собственном сайте**: товар должен быть промаркирован,
а при продаже коды выводятся из оборота через онлайн-кассу.

Для интеграций это значит:

- Маркет: коды передаются по заказу (метод `identifiers`/`boxes`), для заказов юрлиц — обязательно;
- Доставка: у позиции заказа есть поле `marking_code`;
- у нас: нужно хранить коды по единицам товара (приёмка → продажа), а GTIN варианта — обязателен.

Точный перечень кодов ТН ВЭД и сроки стоит сверить на сайте «Честного знака»: источники
расходятся в датах (март/август 2025).

## 5. План работ

| Этап | Содержание | Зависит от |
|---|---|---|
| 0. Данные | вес/габариты по типам, GTIN, исправление выгрузки (текстовые колонки), справочники цветов/размеров, типы для псевдокатегорий | бизнес, поставщик |
| 1. Модель | `barcode`, вес/габариты у варианта; структурированный адрес и ПВЗ у заказа; источник заказа; сущность «Отправление»; импорт штрихкода | — |
| 2. Яндекс Доставка | модуль API, расчёт и выбор ПВЗ при оформлении, создание заявки, статусы, ярлыки | этап 1, кабинет Доставки |
| 3. Оплата | онлайн-оплата или `postpay` | решение бизнеса |
| 4. Яндекс Маркет | маппинг категорий, выгрузка каталога, цены/остатки, приём заказов, статусы | этапы 0–1, кабинет Маркета |
| 5. Маркировка | хранение кодов по единицам, передача в Маркет/Доставку, касса | регистрация в ГИС МТ |
