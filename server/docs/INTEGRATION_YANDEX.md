# Интеграция с Яндекс Доставкой и Яндекс Маркетом

Анализ возможности интеграции: что проверено на практике, что нужно доработать в коде и каких
данных не хватает. Проверка данных — на реальной выгрузке поставщика `temp-dev/shel_data_new.xlsx`
(35 829 вариантов, 4 586 артикулов) командой `npm run audit:marketplace`.

Что уже сделано на ветке, свежие цифры импорта и открытые вопросы по файлам соответствий цветов и
размеров — [INTEGRATION_STATUS.md](INTEGRATION_STATUS.md).

## Коротко

| | Возможно? | Главный блокер |
|---|---|---|
| **Яндекс Доставка** (доставка заказов с сайта в ПВЗ и курьером) | Да, API подходит полностью | Нет веса и габаритов товаров; нет договора и склада в кабинете Доставки |
| **Яндекс Маркет** (продажа каталога на маркетплейсе) | Да | Маркировка «Честный знак» (бельё — обязательная с 2025 г.); маппинг категорий и характеристик; 6,5% штрихкодов — внутренние |

Обе интеграции упираются не столько в код, сколько в **данные и юридическую часть**: вес/габариты,
GTIN, коды маркировки, договоры. Код можно писать параллельно с подготовкой данных.

| Состав | 1 053 (2,9%) | |

| **Размер сопоставлен** (`sizes.xlsx`) | 139 (0,4%) | `UN` (универсальный), `45/47`, детские `3/4`, `9/10`, `11/12` |
| **Вес брутто** | **35 829 (100%)** | колонки нет |
| **Габариты упаковки** | **35 829 (100%)** | колонки нет |

Итог: **92,2% вариантов (85,8% артикулов целиком) проходят обязательные поля карточки Маркета**;
**0% готово к Доставке** — нет веса и габаритов.

Найдено при проверке:

- **Excel портит данные.** Детские размеры «3/4», «11/12» сохранены как даты (число 45750 = 03.04.2025).
  Импорт теперь восстанавливает их (`normalizeSupplierSize`), но в `sizes.xlsx` таких размеров нет.
  В `shell_data_short.xlsx` штрихкоды испорчены необратимо (`8,42209E+12`). Выгрузку нужно делать
  с текстовым форматом колонок «Штрих-код» и «Размер».
- **28% строк — в псевдокатегориях**, а не в типах товара: «Коллекция …» (10 112), «Распродажа»
  (1 086), «Образцы» (902), «Некондиция» (101), «Уценка» (26). Маркету нужен тип («Бюстгальтер»),
  и на нашем сайте это тоже засоряет каталог.
- **Остаток «>5» у 12 845 строк (36%)** — точное количество неизвестно. Импорт берёт 5; для Маркета
  это риск продать больше, чем есть, либо недопоказ остатка.
- **Импорт не читает штрихкод вообще**, и в БД для него нет поля.

### Яндекс Доставка — тестовый контур

Запросы к `b2b.taxi.tst.yandex.net` с публичным тестовым токеном из документации:

| Метод | Результат |
|---|---|
| `location/detect` | ✔ «Москва» → `geo_id` 213 |
| `pickup-points/list` | ✔ 838 ПВЗ в Москве, из них **94 с примеркой** (`is_fitting_allowed`) |
| `offers/create` (наш товар, ПВЗ и курьер) | Запрос проходит валидацию; варианты не выдаются: публичный тестовый склад без настроенных заборов (`pickups_not_configured`, `no_delivery_options`) |
| `offers/create`, курьер с оплатой картой при получении | ✘ `card_on_receipt` для курьера запрещён — нужен `postpay` |
| `pricing-calculator` | `no_delivery_options` — та же причина |

Вывод: формат заказа подходит, полный цикл (заявка → подтверждение → ярлык → статусы)
проверим на своём тестовом складе после подключения кабинета. Важно для белья: **примерка**
(`fitting` у позиции и `is_fitting_allowed` у ПВЗ) и **частичный выкуп** (`particular_items_refuse`).

У Маркета публичной песочницы нет: все методы требуют API-ключ кабинета продавца.

## 2. Яндекс Доставка

### Какой продукт

- **«Доставка в другой день»** (API платформы, `/api/b2b/platform/…`) — ПВЗ, постаматы и курьер
  по России. Основной вариант для магазина.
- «Экспресс» (`/b2b/cargo/integration/v2/claims…`) — курьер за 1–2 часа по городу. Имеет смысл
  позже, только для Москвы и при наличии склада в городе.

### Как встраивается в магазин

1. **Корзина / оформление**: покупатель выбирает ПВЗ на карте (`pickup-points/list`, виджет) или
   вводит адрес; бэкенд считает стоимость и срок (`pricing-calculator`) и показывает их.
2. **После подтверждения/оплаты заказа**: `offers/create` → выбрать оффер → `offers/confirm` →
   сохранить `request_id`.
3. **Отгрузка**: ярлыки (`request/generate-labels`) и акт приёма-передачи — в админке.
4. **Статусы**: периодический опрос `request/info` (cron, как ретраи Telegram) → статус заказа у нас
   и уведомление покупателю.
5. **Отмена**: `request/cancel`.

### Что доработать в коде

- **Товар/вариант**: вес брутто (г) и габариты (см) — на уровне варианта или «типовой упаковки»
  подкатегории (для белья обычно хватает 2–3 типоразмеров пакета).
- **Заказ**: структурированный адрес (город, улица, дом, квартира, индекс, координаты) вместо
  `region` + `address`; раздельные имя и фамилия; выбранный ПВЗ; стоимость доставки в сумме заказа.
- **Новая сущность «Отправление»**: `request_id`, оффер, статус, история статусов, трек, ярлык.
- **Способы доставки**: `DeliveryType` сейчас — справочник с названием; нужен провайдер
  (`yandex_pvz`, `yandex_courier`, `manual`) и расчёт цены.
- **Модуль `YandexDeliveryModule`**: клиент API (таймауты, ретраи, лимиты), cron статусов, эндпоинты
  для фронта (список ПВЗ, расчёт), действия в админке (создать заявку, ярлык, отменить).
- **Фронт** (минимально): выбор ПВЗ/адреса и показ стоимости на странице оформления.
- **Оплата**: сейчас её нет — заказ создаётся без оплаты. Для Доставки варианты: `postpay` (оплата
  при получении, комиссия Доставки) или онлайн-оплата (ЮKassa и т. п.) → `already_paid`.

### Каких данных не хватает

| Данные | Где взять |
|---|---|
| Договор и кабинет Яндекс Доставки, боевой токен | личный кабинет |
| `platform_station_id` склада отгрузки | выдаёт менеджер Доставки |
| Вес и габариты товаров/упаковок | замерить по типам товаров |
| ИНН, ставка НДС магазина (`billing_details`) | бухгалтерия |
| Политика: примерка, частичный выкуп, оплата при получении | решение бизнеса |

## 3. Яндекс Маркет

### Модель работы

| Модель | Кто хранит и доставляет | Подходит |
|---|---|---|
| **DBS** | склад и доставка — продавец (можно через Яндекс Доставку) | ✔ проще всего: свой склад, своя логистика, коды маркировки не проверяются в ГИС МТ при приёмке Маркетом |
| **FBS** | склад продавца, доставка — Маркет | ✔ если удобнее отгружать Маркету; коды маркировки проверяются |
| FBY | склад Маркета | позже, при большом обороте |

Рекомендация: начать с **DBS** (или FBS) — товар остаётся на своём складе, остатки общие с сайтом.

### Как устроена интеграция (Partner API)

1. **Каталог**: `POST v2/businesses/{businessId}/offer-mappings/update` — `offerId` (наш код варианта),
   `name`, `marketCategoryId` (листовая категория), `pictures` (1–30 постоянных ссылок), `vendor`,
   `description` (≤ 6000), `barcodes` (GTIN), `weightDimensions` (см, кг), `manufacturerCountries`,
   `parameterValues` (характеристики категории: размер по сетке, цвет, состав, пол…); до 100 товаров
   за запрос. Характеристики — `offer-cards/update`.
2. **Цены и остатки**: отдельные методы цен и остатков (`offers/stocks`) — по cron и при изменении.
3. **Заказы**: уведомления Маркета на наш эндпоинт или опрос списка заказов → создание заказа у нас
   с источником «Маркет», резерв остатка, смена статусов (принят, собран, отгружен).
4. **Маркировка**: коды «Честного знака» по каждой единице —
   `PUT v2/campaigns/{campaignId}/orders/{orderId}/identifiers` (DBS) или `…/boxes` (FBS).
5. **Возвраты и отмены**: обработка статусов и возврат остатка.

### Что доработать в коде

- **Вариант товара**: `barcode` (GTIN) — сейчас колонка выгрузки игнорируется; вес и габариты (общие
  с Доставкой); `marketSku` и статус карточки на Маркете.
- **Маппинг категорий**: таблица «категория/тип поставщика → листовая категория Маркета» и набор
  характеристик категории (размерная сетка, цвет Маркета, пол, материал). 185 пар категория/тип в
  выгрузке, из них 28% строк — псевдокатегории, их тип придётся выводить из названия.
- **Тексты**: описания короче 400 символов у 90% — нужна доработка контента (вручную или генерацией).
- **Модуль `YandexMarketModule`**: клиент API (ключ `Api-Key`, лимиты), синхронизация каталога,
  цен и остатков (cron + по событию), приём заказов, статусы, маркировка.
- **Общий остаток**: заказы с сайта и с Маркета списывают один склад — нужна быстрая выгрузка
  остатков на Маркет после каждого заказа, иначе перепродажа.
- **Заказ**: поле источника (сайт / Маркет), внешний номер заказа.

### Каких данных не хватает

| Данные | Объём | Где взять |
|---|---|---|
| **Коды маркировки «Честный знак»** на каждую единицу | весь ассортимент | регистрация в ГИС МТ, заказ кодов у производителя/поставщика или самостоятельно |
| GTIN вместо внутренних штрихкодов | 2 343 варианта | GS1 RUS (префикс предприятия) или у поставщика |
| Исправить невалидные штрихкоды | 11 | поставщик |
| Описания ≥ 400 символов | ~90% | контент |
| Сопоставить цвета и размеры | 576 + 139 строк | дополнить `colors.xlsx`, `sizes.xlsx` |
| Тип товара для псевдокатегорий | 28% строк | правила по названию или вручную |
| Вес и габариты | 100% | замер |
| Кабинет продавца, `businessId`, `campaignId`, API-ключ | — | регистрация на Маркете (ИП/ООО) |
| Размерные таблицы | по брендам | производители / таблицы Маркета |

## 4. Маркировка «Честный знак» — до любых интеграций

Нижнее бельё, купальники, чулочно-носочные изделия и домашняя одежда входят в «третью волну»
обязательной маркировки лёгкой промышленности (Постановление Правительства № 883, 2024 г., старт
в 2025 г.). Это касается **и продаж на собственном сайте**: товар должен быть промаркирован,
а при продаже коды выводятся из оборота через онлайн-кассу.

Для интеграций это значит:

- Маркет: коды передаются по заказу (метод `identifiers`/`boxes`), для заказов юрлиц — обязательно;
- Доставка: у позиции заказа есть поле `marking_code`;
- у нас: нужно хранить коды по единицам товара (приёмка → продажа), а GTIN варианта — обязателен.

Точный перечень кодов ТН ВЭД и сроки стоит сверить на сайте «Честного знака»: источники
расходятся в датах (март/август 2025).

## 5. План работ

| Этап | Содержание | Зависит от |
|---|---|---|
| 0. Данные | вес/габариты по типам, GTIN, исправление выгрузки (текстовые колонки), справочники цветов/размеров, типы для псевдокатегорий | бизнес, поставщик |
| 1. Модель | `barcode`, вес/габариты у варианта; структурированный адрес и ПВЗ у заказа; источник заказа; сущность «Отправление»; импорт штрихкода | — |
| 2. Яндекс Доставка | модуль API, расчёт и выбор ПВЗ при оформлении, создание заявки, статусы, ярлыки | этап 1, кабинет Доставки |
| 3. Оплата | онлайн-оплата или `postpay` | решение бизнеса |
| 4. Яндекс Маркет | маппинг категорий, выгрузка каталога, цены/остатки, приём заказов, статусы | этапы 0–1, кабинет Маркета |
| 5. Маркировка | хранение кодов по единицам, передача в Маркет/Доставку, касса | регистрация в ГИС МТ |
